# Audit, execution and idempotency

The trusted executor alone holds DML on workflow tasks/escalations/notes/assignments. It has SELECT only on historical business/knowledge tables. Agent reader has no workflow DML. Authentication can access password/token hashes; ordinary workflow roles receive only safe principal/session columns. No workflow role has DELETE/TRUNCATE or audit UPDATE. Runtime connections reject database owners, superusers, BYPASSRLS and role/database creators.

An execution locks the proposal, verifies one current distinct approval, writes EXECUTING and a started receipt/event, then performs the real business mutation in a nested PostgreSQL savepoint. Mutation, action event, completed event, receipt and terminal proposal commit atomically. If a mutation or final receipt fails, that savepoint rolls back all business effects and success events; the surrounding transaction retains a FAILED receipt/proposal and failure audit. A disconnected client must retry with its original key and inspect the durable receipt; commit acknowledgement is not exactly-once network delivery.

Unique proposal_id on executions and row/advisory locks prevent duplicate effects. Idempotency-Key is a UUID, persisted and bound to actor, operation and canonical request digest. Identical authorized retries return the stored response after commit; changed body/operation/actor returns 409. Denied request results may also be bound, so a later intended operation uses a fresh key. Cached responses are not returned before current permission/ownership checks. Replays append audit events. Completing the same proposal with a different key returns its same receipt, without another mutation.

Database triggers enforce approved active execution context for task/escalation writes and append-only child writes, restrict the writable task columns to the approved action category, require target/version and preserve provenance. These reinforce the typed executor; they are not a substitute for guarding the service login or owner credentials. Functions run with invoker rights, never SECURITY DEFINER.

Audit rows contain actor, timestamp, department, action, object, proposal/execution, request correlation ID, before/after state, reason and result. Receipts link real affected IDs and audit event IDs. Notes, assignment history, evidence, policies, approval decisions, audit and idempotency records reject UPDATE/DELETE. Terminal receipts reject rewriting. Administrator policy/role decisions are audited. Bootstrap identifies its trusted maintenance origin. Authentication failure auditing avoids passwords and tokens.

This is database-enforced append-only application history, not external cryptographic WORM storage. The database owner/host administrator can disable triggers or alter schema. Protect those credentials separately. Body parsing/authentication failures have safe responses; authenticated business denials are durable. Audit denial collection for malformed/read requests is best effort when the database itself is unavailable; availability does not grant permission.

References: [PostgreSQL explicit locking](https://www.postgresql.org/docs/current/explicit-locking.html), [SQLAlchemy transactions](https://docs.sqlalchemy.org/en/20/orm/session_transaction.html).
